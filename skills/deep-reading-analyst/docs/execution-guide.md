# Deep Reading Analyst — 执行指南

> 本文档由 `/deep-reading [path]` 触发后按需读取。
> 路由: `/deep-reading` → `SKILL.md`（框架定义 + 参数） → 本文件（执行步骤）

## Step 1: 预扫描

### 1.1 读取文档

```bash
wc -l <file>  # 判断长度
head -50 <file>  # 快速扫描开头
```

### 1.2 判断属性

| 属性 | 判断方式 |
|------|---------|
| **文档类型** | 对话转录 / 观点文章 / 研究报告 / 技术方案 / 商业分析 |
| **长度** | ≤300 行 → Standard; >300 行 → Deep（用户可 override） |
| **语言** | 中文 / 英文 / 混合 → 分析语言与原文一致 |
| **已有 frontmatter?** | 有 → 读取 subject/tags 作为上下文 |

### 1.3 框架选择

根据 SKILL.md 框架选择指南表，确定使用哪些框架。

**优先级**: 用户 `--framework` 指定 > 文档类型匹配 > 默认 fallback

**混合文档处理**（如"研究报告含对话节选"）：
- 按主体类型选框架（占比 >60% 的部分决定类型）
- 如果无法判断主体 → 使用 Critical Thinking + Systems Thinking（最通用组合）
- Deep 模式下不受影响（全部 5 个框架都用）

### 1.4 大文件策略

| 文件大小 | 策略 |
|---------|------|
| ≤500 行 | 直接全文阅读 |
| 500-2000 行 | 分段阅读，每段 500 行，最后综合 |
| >2000 行 | 分块 + subagent 并行分析，最后综合（对齐 process-inbox） |

分块时每块保留 50 行上下文重叠，避免断裂。

## Step 2: 框架分析

### 执行顺序

1. 先执行所有选定框架的分析
2. 每个框架独立输出，不要在一个框架中引用另一个框架的结论
3. 框架分析时紧贴原文，引用具体段落/语句作为证据

### 分析质量要求

- **具体**: "论证薄弱" → "第 3 段的因果推导缺少中间环节：从'AI 能模拟共情'直接跳到'AI 可以替代教练'，缺少对共情深度的区分"
- **平衡**: 不要只找缺陷，同时指出论证有力的地方
- **原文锚定**: 每个发现至少引用一处原文
- **避免过度解读**: 区分"作者明确说的"和"可能暗示的"

### 对话转录特殊处理

对话转录与文章不同：
- 多个发言人 → 分别追踪每人的立场和论点
- 对话有推进过程 → 注意观点的演变和收敛
- 口语化表达 → 不要对口误或不完整句子苛求逻辑严谨
- 共识 vs 分歧 → 明确标注哪些是共识、哪些存在分歧

## Step 3: 综合

### 3.1 交叉印证

检查不同框架的发现是否相互支持或矛盾：
- 框架 A 发现的假设 vs 框架 B 发现的系统约束 → 是否一致？
- 多个框架指向同一个盲点 → 高置信度发现
- 框架间矛盾 → 标注为"待进一步探讨"

### 3.2 核心洞见提炼

从所有框架分析中提炼 3-5 个核心发现：
- 每个发现用 1-2 句话概括
- 按重要性排序（最重要的在前）
- 标注支撑该发现的框架来源

### 3.3 盲点识别

列出原文未覆盖但可能重要的角度：
- 缺失的利益相关方视角
- 未考虑的时间维度
- 被简化的复杂性
- 可能的反面证据

## Step 4: 输出与项目集成

### 4.1 生成分析报告

按 SKILL.md 定义的输出格式生成报告。

**文件命名**: `YYYY-MM-DD-[关键词]-分析.md`（与 process-inbox 惯例一致，用 frontmatter `type: deep-reading-analysis` 区分）

### 4.2 确定写入路径与模式

**核心原则（CRITICAL）**: 分析报告是 **AI 生成的衍生品**，不是用户原创内容。**禁止**将分析报告放入用户原创主题目录（如 `preferences/`, `life/`, `content/`, `relationships/`），否则会污染主题目录的"主体纯度"。

**路径选择**（按存在顺序回退）:

1. 若项目有 `knowledge-base/ai-generated/analysis/` → **首选**（推荐惯例）
2. 若项目有 `knowledge-base/knowledge/analysis/` → 次选
3. 若项目有 `knowledge-base/` 但无以上子目录 → 创建 `ai-generated/analysis/` 后写入
4. **若项目无 `knowledge-base/` 结构** → 输出到当前工作目录下的 `YYYY-MM-DD-[关键词]-分析.md`，或由 `--output` 参数指定

**独立文件 vs 追加到原文档**:

| 条件 | 模式 | 说明 |
|------|------|------|
| 任何 AI 分析报告 | **独立文件**（默认） | 走"AI 产出 vs 人类原文"分离原则 |
| 分析结果 <200 字 + `--output inline` | **追加到原文档末尾** | 唯一例外：极短补注，在 `---` 分隔符后追加"## 深度阅读分析"部分 |

**写入路径表**:

| 原文位置 | 分析报告位置 | 备注 |
|---------|-------------|------|
| 任意位置（包括 inbox/、knowledge-base/conversations/、knowledge-base/knowledge/、外部 URL） | `knowledge-base/ai-generated/analysis/`（首选）→ `knowledge-base/knowledge/analysis/`（次选） | 用 frontmatter `source:` 字段保持与原文的可追溯链接，**不靠物理同目录** |

**禁止**（适用于有 knowledge-base 结构的项目）:

- ❌ 把分析报告放进 `preferences/`、`life/`、`content/`、`relationships/`、`work/` 等用户原创主题目录
- ❌ 看到目录里有相关主题的文件（如 principles/ 里有原则文件），就用单样本类比把分析放进去 — 必须先看完整目录的语义角色（README / 多个文件统计），确认这是"AI 产出收纳目录"还是"用户原创目录"
- ❌ 把"主题相关"等同于"目录正确"

### 4.3 Idea 检测与路由

分析过程中检测以下信号（复用 process-inbox 三路分流逻辑）：

**信号类型与路由**:

| 信号 | 路由目标 | 动作 |
|------|---------|------|
| 可行动的商业想法 | `inbox/ideas/` | 创建 idea 文件，标注来源为本次分析 |
| 值得深入研究的课题 | `/research-chain` | 询问用户是否启动研究链 |
| 可以写成内容的独特洞见 | `/capture-topic` | 询问用户是否录入选题池 |
| 对现有项目的改进建议 | 报告内列出 | 不自动路由，留给用户决定 |

**Research Chain 触发条件**（满足任一即提示）：
- 分析中发现需要 >3 个外部数据源才能验证的论点
- 涉及新兴领域且 knowledge-base 中无相关文档
- 对话中明确提到"需要进一步研究"/"值得深挖"

**执行顺序**:
1. 在报告末尾"检测到的素材/想法"部分列出所有检测结果
2. 分析完成后，统一询问用户（不在分析过程中打断）：

```
检测到 N 个可行动项：
1. [商业想法标题] — 写入 inbox/ideas/? (Y/n)
2. [内容素材标题] — /capture-topic? (Y/n)
3. [研究课题标题] — /research-chain? (Y/n)
```

3. 如果用户使用了 `--no-idea` 参数，跳过此步骤

### 4.4 关联现有知识

分析完成后，搜索 knowledge-base 中的相关文档：
```bash
# 用关键词搜索相关内容
grep -rl "[关键词]" knowledge-base/ | head -5
```

如果找到相关文档，在报告中添加"相关文档"部分，标注与本次分析的关联。

### 4.5 完成确认

```
深度阅读分析完成:
- 来源: [文档路径]
- 深度: Standard / Deep
- 框架: [使用的框架]
- 报告: [输出文件路径]
- 核心发现: N 个
- 检测想法: N 个
```

## 错误处理

| 场景 | 处理 |
|------|------|
| 文件不存在 | 提示用户检查路径 |
| 文件为空 | 提示"文件为空，无法分析" |
| 非文本文件 | 提示支持的格式：.md, .txt, .pdf |
| 分析中发现内容不足 | 降级到 Standard，告知用户原因 |

## 自检清单

- [ ] 是否读取了完整文档（大文件是否分块完整）？
- [ ] 框架分析是否紧贴原文（有引用）？
- [ ] 核心发现是否具体、可验证？
- [ ] 盲点识别是否有价值（不是泛泛而谈）？
- [ ] 输出文件是否有正确的 frontmatter？
- [ ] Idea 检测是否执行？
- [ ] 是否询问用户关于检测到的想法/素材？
